## Graph collector binary spec (living document — `jzombie/jzombie-graph`)

This spec lives in the collector's own repo as its record of decisions: it compiles every collector decision from the design thread, tracks the shipped implementation, and is updated as decisions (names, paths, cadences) are made. It was originally written as an appendix comment to be lifted into an issue once the repo existed — that happened; the plan file is now the home.

### What it is
A standalone Rust binary: point it at a GitHub user/org, get back visibility-flagged portfolio graph JSON. Name locked: `jzombie-graph` (`jzombie/jzombie-graph`, explicitly personal-scope — not magnet-branded, no crates.io claim implied; rename only if a generic extraction ever ships). It becomes its own Tier 2 proof artifact: tested, versioned, released, with a row on this profile earned by serving the pipeline that renders it. **Name (decided Nov 8, 2026): `portfolio-graph`** — this output is one *particular* graph and the same machinery may back other graphs later (other scopes, other edge meanings), so it carries its own name rather than "the graph". The name keys the published paths (see Publishing) and every related asset shares the stem: `portfolio-graph.json`, `portfolio-graph-schema.json`, `portfolio-graph.md`. The binary's own name is separate and stays locked.

### Why a Rust binary (not DSL, not gh+jq)
- **Not OxDock DSL:** collection is retries, backoff, pagination cursors, malformed-JSON tolerance — I/O failure modes DSLs handle worst. DSL owns scoring/layout/render (data logic); the binary owns fetching (thin layer grown up). HTTP layer reuses `rust-reqwest-drive` (existing retry/backoff via `DriveThrottleBackoff` throttle-only mode — no cache file, no new client logic). Unless OxDock ever grows a real HTTP module, DSL-side fetching is reimplementing reqwest badly.
- **Drive note (Nov 7):** integrated now (`reqwest-drive 0.13.x`, `ThrottlePolicy { base_delay_ms: 200, jitter: 100, max_concurrent: 5, max_retries: 3 }`). Contents decoding uses the `base64` crate — no hand-rolled crypto/encoding anywhere. Known cost: the middleware retries any non-2xx including 404s, so fail-open 404 probes (missing manifests) cost up to `1 + max_retries` calls worst-case; the pre-fetch budget estimate accounts for it. Per-request 404 bypass (no-retry on fail-open probes) is the follow-up if the budget bites.
- **Not `gh`+`jq` bash:** untestable glue with exactly the pagination/rate-limit failure modes tests catch — recreates what OxDock exists to replace.
- **Rust specifically:** the principal's stack (dogfooded), proper error handling, parallel fetches.

### Where it lives and runs
Own repo (extraction, per the term-wm precedent — tooling outlives the project that births it). Run by the Actions thin layer on the daily cron: Actions owns trigger + token + execution; the binary owns enumeration and parsing; OxDock owns everything downstream. The profile repo stays presentation + config (values, templates, DSL logic) with fast renders and readable source. Amusing structural note: the profile pipeline *uses* the collector, which is itself a workflow edge in the graph — the collector appears in the map it builds.

### Automation posture (platform facts verified Nov 8, 2026)
Every number below was read off GitHub's own docs or measured live (headers curl'd, endpoints probed), not second-hand from vendor blogs — the research round this came from contained one fabricated reliability study, so sourcing is recorded here deliberately.

- **Token identity:** `GITHUB_TOKEN` is scoped to the repository containing the workflow — it cannot enumerate the user's other repos, so the sweep authenticates with a fine-grained PAT (read-only: metadata + contents; deliberate expiry, deliberate rotation). Rate headroom: PAT = 5,000 requests/hour; `GITHUB_TOKEN` = 1,000 requests/hour REST (1,000 points/hour GraphQL) per repository. A full sweep is a few hundred calls — the PAT is for *reach*, not rate. Explicit `permissions:` block either way (defaults have been read-only since Feb 2023). Commits made with `GITHUB_TOKEN` don't trigger other workflows (no cascade loops) and land as `github-actions[bot]`.
- **Ceilings that actually apply:** secondary limits — 100 concurrent requests (the throttle policy's `max_concurrent: 5` is 20× under), 900 points/min REST, 2,000 points/min GraphQL, 90s CPU per 60s real time; content creation via API/web interface is capped at 80/min and 500/hour (irrelevant at daily cadence); **git pushes carry no documented numeric limit at all** — they aren't API requests, so the AUP's "excessive automated bulk activity" clause is the only line, and one gated daily commit is nowhere near it. Conditional requests (ETag → 304) don't count against the primary limit — free re-checks wherever the API returns ETags.
- **Cron is best-effort:** documented floor is one run per 5 minutes; runs queue behind global load (worst at the top of every hour) and can be dropped silently — offset the schedule (`17 4 * * *`), never `0 * * * *` for anything noticed. Public repos auto-disable scheduled workflows after 60 days without repository activity; whether bot commits count as "activity" is undocumented with conflicting community reports — cheap insurance until proven: the milestone-2 metrics commit lands daily anyway, plus one human commit a month or a `workflow_dispatch` fallback.
- **No `pull_request_target` anywhere:** blocked by default in public repositories from Dec 2, 2026 (changelog Nov 2, 2026). Nothing in this spec needs it; nothing here may add it.
- **ToS posture:** the daily sweep is the green case — seconds-long, low-burden, and about this repository's own project (the two Actions-terms clauses: burden-disproportionate to users; runner activity unrelated to the project). The bright line established by the research round is commit churn: 15-minute README/metrics rewrites approach "excessive bulk activity"; daily, gated-on-change appends do not. Pipeline cadences elsewhere in this system stay ≥ hourly for the same reason.
- **Delivery:** published artifacts ride GitHub Pages via `actions/upload-pages-artifact` + `actions/deploy-pages` (bypasses the 10-builds/hour branch-publishing soft limit; `permissions: contents: read, pages: write, id-token: write`; limits — 10-minute deploy, 1 GB site, 100 GB/month soft bandwidth — sit orders above need). Measured headers (Nov 8): Pages sends `cache-control: max-age=600` (fixed, not configurable — consumers see up to 10 minutes of staleness) and `access-control-allow-origin: *` (cross-origin browser fetch works); `raw.githubusercontent.com` sends `max-age=300` and **no CORS header** — cross-repo reads use Pages, never raw. The publish-then-consume pattern itself is well precedented (git scraping since 2020, GitHub Next's Flat Data, scheduled-Pages rebuilds 2021–22), so none of this is novel-risk territory.

### Publishing (daily workflow → GitHub Pages)
- **One workflow, two triggers:** runs once every 24 hours on cron (offset off the top of the hour, per the scheduling bullet above) and is also `workflow_dispatch`-triggerable by hand. The manual trigger is both the "regenerate now" button and the debugging lane — dispatch runs bypass the scheduled queue, so it also covers any dropped or delayed cron slot without waiting a day.
- **Run sequence:** `jzombie/rust-oxdock/.github/actions/setup-oxdock@main` (engine tracks `latest` by default; we own both ends) → `oxdock .github/scripts/pipeline.oxfile`, which owns build (`cargo build --release --workspace`) → collect (`jzombie-graph --user jzombie --format json`, authenticated with the PAT secret) → schema (`--format schema`, static, no API and no graph data) → render (`cartographer` reads the staged JSON, re-validating through `Graph::from_json`, writes the fragment) → deploy the `data/` dir as the Pages artifact. OxDock owns the orchestration (consistent with "OxDock owns everything downstream"); Actions owns trigger + token + execution. The script is fail-closed — a failing RUN stops the pipeline immediately — so failure at any stage means no new deployment and Pages keeps serving the last good one (stale-but-up, never broken). Using oxdock this way creates no graph edge (`run:` steps are invisible to the workflow scanner; dogfooding without disturbing the taxonomy — a deliberate choice, see the workflow-as-association decision). The workflow's `permissions:` stay `contents: read, pages: write, id-token: write` — CI never writes to the repo; the milestone-2 metrics commit job is deliberately a separate workflow so this one keeps zero write access to code. Path source of truth is `src/paths.rs` (neither YAML nor the DSL can import it — both mirror the constants by hand).
- **What it publishes — the path layout is the API:** each run regenerates the assets and deploys them via the `upload-pages-artifact` + `deploy-pages` posture above, placing each asset at a fixed, typed path so the site always serves the latest run's output and other projects link paths instead of hunting through a directory listing:
  - `json/portfolio-graph.json` — the graph data.
  - `json/portfolio-graph-schema.json` — the generated schema, paired beside the data it validates.
  - `markdown/fragments/portfolio-graph.md` — the cartographer's rendered output, verbatim (next bullet).

  Directory names carry the type; file names carry the graph's own name — `portfolio-graph` (decided Nov 8, 2026), the same stem for data, schema, and rendering so the published set reads as one asset group. Every future graph slots in as one more `json/<name>.json` + `json/<name>-schema.json` + `markdown/fragments/<name>.md` triple with no further layout decisions — and keying the fragment by *graph* (not renderer) is what keeps two graphs from colliding at one URL. The renderer is code-only: its name never appears in a published path. Local working copies live under the gitignored `data/` tree (same relative layout as the site); after the first publish the assets are fetched from Pages, never committed. The one committed exception is the schema expectation at `json/portfolio-graph-schema.json` — source for the drift test, not generated data. The published paths are the contract and only ever gain entries, never change.
- **The fragment is a transport, not a transform:** it carries the cartographer's text output **verbatim — byte-for-byte what the renderer emits today, unchanged**: no reformatting, no wrapping, no conversion to GitHub-flavored prose. Any future change to what the renderer draws is a content change behind the same URL; the pipeline itself never edits the bytes. Other projects include or link it directly.
- **TODO (principal): custom domain** — once the Pages site exists, hook a domain up to it (DNS records + Pages domain settings). Presentation only; nothing in the pipeline depends on it, but the fragment/JSON URLs are meant to be linkable from elsewhere, so the domain is the human step after the first deploy.
- **Rename decided (Nov 8, 2026): `cathedral` → `cartographer`** — what it does is select, place, and route the portfolio diagram, i.e. draw a map of the graph from data. Mechanical rename, landed before the fragment URL and docs ship: `crates/cathedral/` → `crates/cartographer/`, package `jzombie-graph-cathedral` → `jzombie-graph-cartographer`, bin `cathedral` → `cartographer`, `render_cathedral` → `render_cartographer`, the crate doc's "zenOSmosis cluster renderer" line, and every README/plan reference. Clippy + the suite prove no logic moved; output bytes must be identical (snapshot suite enforces).

### Inputs: fail-open collection
- Enumerate everything owned by the user/org, **forks included** — fork status (`fork: true`, API-native) rides along as a node fact, not a verdict. Default views exclude forks; two mechanical rules re-admit them: **(a) divergence** — fork `ahead_by` N commits vs upstream (compare API, computable) counts as own work and includes it, still labeled fork (`term-wm-vt100` is the reference case); **(b) load-bearing** — a fork with fan-in from portfolio repos is structurally load-bearing and includes regardless (a portfolio repo depending on your fork is a real edge, not a study copy). No allowlist: new repos join by existing. The Tier 3 isolation rule (≥1 portfolio edge or omit) does the remaining junk filtering automatically — most study-forks point upstream at other people's repos, have no portfolio edges, and self-omit. Collect everything; let the graph decide what shows.
- **All branches**, not default-only (verified: GitHub's SBOM API is default-branch-only and therefore unusable for this). Union edges across branches; each edge carries the recency of the most recent branch declaring it.
- Manifests: `Cargo.toml` first (deps + build-deps; **dev-deps excluded** — test-only coupling isn't architectural), then package.json / pyproject / go.mod where present. Workspace members (`crates/` subdirs) walked recursively via git trees API and collapsed to the repo node — internal structure, not portfolio edges.

### Edge taxonomy (all mechanically collected; dependence weighed, associations shown)
| kind | source | contributes to node weight? |
|---|---|---|
| `manifest` | Cargo.toml etc., all branches | **yes** — declaring workspace-member count × scope (`optional` → 0.5, else 1.0) × use-site Boolean (0/1 from AST parsing in the collector; zero references nullifies; unparseable files count as matches; every nullification logged in the briefing digest; regex scan documented fallback), unioned across branches |
| `submodule` | `.gitmodules` | **yes** — 1.0 flat (indivisible pin) |
| `registry` | crates.io reverse-deps API (npm/PyPI equivalents where free) | **yes** — as manifest (published coupling counts like declared coupling) |
| `lockfile gate` | Cargo.lock / package-lock / poetry.lock, all branches | **gate, not weight** — package present at any version confirms the edge; absent-with-lockfile deletes it as unresolvable; no lockfile → manifest suffices. Resolved versions recorded as briefing facts (technical lag), never scored |
| `workflow` | `uses: owner/repo`, sibling checkouts, matrix refs | no — displayed association (pipeline depends, repo doesn't; revisit on logged counter-evidence) |
| `docs` | README/llms.txt links to siblings | no — displayed association |
| `xrefs` | issue/PR bodies referencing sibling repos | no — displayed association |

### Per-ecosystem implementation (same shape, local tools)
| mechanism | Rust | Node | Python |
|---|---|---|---|
| manifest parse | Cargo.toml (`[dependencies]`, `[build-deps]`, `[workspace]`); dev-deps excluded | package.json (`dependencies`; `peerDependencies`/`optionalDependencies` → 0.5 scope) | pyproject.toml / requirements.txt (extras markers → 0.5 scope) |
| member counting | workspace members declaring | npm-workspaces members declaring | packages declaring (monorepo: per-package) |
| lockfile gate | Cargo.lock (package present?) | package-lock.json / yarn.lock / pnpm-lock.yaml | poetry.lock / Pipfile.lock / frozen requirements |
| use-site check | **syn AST walk** (`use` items incl. `pub use`; unparseable file = match); regex identifier scan documented fallback | **swc_ecma_parser AST walk** (import decls + `require` calls); regex fallback | **rustpython-parser AST walk** (`Import`/`ImportFrom` nodes); regex fallback |
| alias mapping | package name → portfolio repo, in values.toml (all ecosystems — names diverge everywhere, this table is the fix) |

All three use-site tools run in the thin collector layer (fast, no full builds). A dep with zero use-sites anywhere is phantom regardless of ecosystem — nullified before fan-in. False positives (generated code, macros) keep the edge, which is the safe direction.

No kind-weights, no tuning protocol — superseded by counted dependence (locked decision 9): edge weight is manifest arithmetic × use-site Boolean, cross-repo edges pass the lockfile existence gate, node weight is summed incoming dependence, ordering is weight-desc/stability-tiebreak. The would-be calibration constants never existed. Workflow-as-association is the one parked judgment, flagged for revisit if a logged disagreement ever traces to it. Complexity rule: VFI and out-degree dampening are implemented alongside 1-level fan-in; whichever flips a Tier 1 boundary ships, the rest stay logged as checked alternatives.

### Privacy rule (locked)
Private repos participate in graph computation as transit nodes (no orphaned chains, true centrality) and are stripped before render: no nodes, stubs, links, counts, or deltas. Scoring sees the true graph; all surfaces show the public subgraph (both endpoints public). Default output is public-only (store-safe, committable); the true graph is gated behind `--include-private` (briefing lane only, never committed).

### Output contract
Node/edge JSON with a stable documented schema. Every node carries a computed `visible` flag (ticking-or-load-bearing per decisions 6/9/12, compiled to data); every edge carries kind, declaring branches, and recency. Renderers filter blindly on the flag — no surface re-decides. JSON-first, OxDock renders; stdout lanes as they ship: `--format dump` (alias `table`) — the full vertical every-node/every-edge debug dump (ten-second value for strangers), `--format dot` for local eyeballing (dev-time only — Graphviz never enters the render pipeline), and `--format focus` reading a stored graph via `--input graph.json` — the offline focus ranking, no API and no token, recomputing `Node::focus` live so the formula never exists in two places. `jq`-queryable JSON from day one. **Schema as a generated asset:** the JSON Schema is derived programmatically from the Rust types themselves (`#[derive(JsonSchema)]` alongside the serde derives on `Graph`/`Node`/`Edge`/`Layer`/`EdgeKind`; serde attributes like `rename_all` and `Option` nullability are honored, doc comments become `description`s, `DateTime<Utc>` renders as `date-time`) — never hand-maintained, so there is no second copy of the contract to drift. It ships as a committed asset (`json/portfolio-graph-schema.json`, same path it publishes under — see Publishing) with a test that regenerates and diffs it, making any struct change that alters the output contract fail CI until the schema is consciously re-committed (the strong form of the `SCHEMA_VERSION` guard in `Graph::from_json`), and it publishes alongside the JSON so consumers get editor validation instead of prose. Snapshot-test requirement: ship with `insta`-style snapshot tests asserting known truths (simd-r-drive fan-in floor, term-wm-vt100 promoted, zero private nodes in public output, llkv present-with-stale-heartbeat) — regressions show as diffs, and the suite is the continuous form of having inspected the graph. The four `jq` recipes that ship as documented examples (no code, day one): who-depends-on-X (filter edges by target), orphans (nodes with zero edges either way), heaviest edges (sort by weight desc, top 20), what-changed (diff yesterday's JSON against today's). Build/run sequence: table with the binary, DOT flag next (one afternoon, see the shape), snapshot tests at implementation, jq recipes the moment the first JSON exists. The private briefing digest (decision 13) inherits all four as its sources — it is the automation of inspections already done by hand, not a new inspection method. The schema also carries velocity/focus facts frozen at collection — `commits_5d`, `commits_30d`, `commit_heat`, `focus`, `last_commit_at` — measured default-branch-only like everything else (a push to a non-default branch must not move focus), captured as of `generated_at` with their inputs alongside so any consumer can recompute or audit. Edge-less repos are still nodes (`layer: "isolated"`): "new repos join by existing" means the JSON, not the drawing — whether a lone box gets rendered is each renderer's call (the cartographer's cluster selection keeps only multi-node components plus docs satellites), never the collector's.

### Why handrolled (verified Nov 7)
`cargo tree`/`guppy` (archived): single-workspace only. GitHub SBOM API: default-branch only. `rgctl` (cited in one report): no independent footprint, unverifiable, and a second engine regardless. Nothing does cross-repo × all-branches × custom edge kinds × private-transit × custom weights — the job is custom by definition. The collector is ~100 lines of enumeration feeding edge-JSON; scoring is counting; layout is BFS. No library needed because libraries solve single-workspace depth and this problem is portfolio breadth.

### Metrics storage (milestone 2 — after first edge-JSON ships)
The traffic API is a 14-day rolling window: unstored, it is deleted daily. Storage here is preservation, not caching. The graph repo is the single home for it — JSONLs live inside `jzombie/jzombie-graph`, never inside the profile repo, the blog, or any portfolio repo. Presentation repos hold config and templates; the collector's own history stays with the collector.

- **Format:** append-only JSONL, one line per repo per sweep. JSON-first, jq-queryable, no database until queries demand one. The `what-changed` recipe already assumes yesterday's file exists — this extends the snapshot concept from structure to metrics.
- **Atomic unit = daily array, not total.** Views and clones both return per-day breakdowns; totals are derived, days are stored. Overlapping 14-day windows then reconcile instead of double-counting, and one snapshot per day reconstructs true daily history. This is the difference between a trend and a pile of samples.
- **Fetch in the binary, read in the DSL.** Traffic fetching is retries, backoff, pagination, rate limits — the exact failure modes the spec assigns to Rust. The daily cron already exists as the trigger; one fetch per day serves every query that day. `GH_TRAFFIC_SWEEP` becomes a reader of the store, not a caller of the API.
- **Private repos are never recorded in the metrics store.** The JSONL is written public-repos-only, filtered at write time — not stripped at render. Rationale: traffic feeds trends, not graph computation (edge weight is manifest arithmetic x use-site Boolean; node weight is summed incoming dependence — no traffic input), so private repos have no reason to be in the file. Structure keeps the original rule (private computes in memory, stripped before render); metrics exclude entirely. Because the store contains only public repos, it commits safely to the public repo, git tracks it as history, and README stats published from it need no filter pass — every count in the file is already public. A private repo's own traffic, if ever wanted, belongs to the decision-13 briefing lane: separate gitignored file, never in this repo, local append plus encrypted vaultclone backup on the `archive-logs.sh` pattern.
- **Honest ceiling:** referrers and paths are top-10 with no daily breakdown. Storing them yields history, not reconstruction. Views and clones are the parts that become true time series.
- **Cadence is the compliance argument:** one gated append per day sits orders of magnitude under every documented ceiling (80 content-creating requests/min, 500/hour; git pushes have no documented quota at all), and Actions artifacts were never the archive anyway — they expire on a ~90-day default; git history is the store, which is the design above. Pretty-print lines with stable keys for readable diffs and merge hygiene; packfile byte-deltas work either way (the research round's "minified JSON kills delta compression" claim was wrong — the real costs are unreadable diffs and key-order churn).
- **README stats lag by construction:** images embedded in READMEs are proxied through camo (undocumented cache, keyed by URL) — a stats image behind a static URL updates only when camo's cache expires, and cache-busting means editing the README, i.e., commits. Publish stats as a link to the Pages-hosted view (measured `max-age=600` — bounded staleness) or accept eventual consistency; don't shape the store around image freshness.

Sequencing is locked: enumeration + edge-JSON first (unblocks Tier 1 and the hub), metrics append second. The binary ships milestone 1 before growing scope — the `~100 lines of enumeration` claim holds until the first JSON exists.
